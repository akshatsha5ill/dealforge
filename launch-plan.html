Section 1

Pre-Launch — Fix What's Broken

Everything that must be done before the app is accessible to users. Divided into critical blockers (app cannot function without these) and important-but-non-blocking work.

1A. Critical Blockers

These must be resolved before any user can access the application. Without these fixes, the client cannot communicate with the server — every API call will 404.

1. Fix: Client Cannot Reach Server Completed

This is the single biggest issue. The client hardcodes BASE_URL = '/api' in client/src/services/api/client.ts, but on Vercel the client and server are on different origins. Every API call fails.

Changes made:

// client/src/services/api/client.ts
const BASE_URL = import.meta.env.VITE_API_URL
  ? `${import.meta.env.VITE_API_URL}/api`
  : '/api';

// client/src/hooks/useWebSocket.ts
const serverUrl = import.meta.env.VITE_API_URL || window.location.origin;
sharedSocket = io(serverUrl, {

4. Fix: Billing Routes Bypass Rate Limiting Completed

server/src/app.ts mounts /api/billing before the apiLimiter. Added a dedicated billingLimiter (30 req/15min) and moved billing routes after the global API limiter with auth + rate limit guards.

The 48-hour window around going live. Focus on monitoring, verification, and immediate fixes.

Day 0: Deploy and Verify

Deploy Sequence

  1. Deploy server to Render first — it has no client dependency. Verify health: GET /api/health
  2. Deploy client to Vercel — with VITE_API_URL pointing to Render server URL
  3. Verify client loads — check browser console for CORS errors
  4. Run smoke tests — full checklist below
